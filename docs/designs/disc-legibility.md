## Problem Statement

The session opened as a UI revamp aimed at toolbar density. It ends somewhere else.
Users report three things: the screen is cluttered, things are hard to find, and **the
text on the disc is hard to read**. Only the third has a measurable physical cause, and
that cause turns out to break the disc's reason to exist: an activity arc whose label
cannot be read, or is not drawn at all, is a coloured band conveying nothing.

## Demand Evidence

Not a market question — an internal tool with real users — so the evidence is what those
users said, plus what the code does.

**From users, unprompted:** cluttered, hard to find, hard to read.

**From the code, measured this session:**

- `renderer.ts:890` sets activity label fill to the literal `'white'`, unconditionally.
- `fillFor` has **five** branches. The default is `colorBy: 'activity'`
  (`renderer.ts:53`, `planner.ts:67`), returning `activity.color` — an opaque hex the
  user picked from a 24-entry `COLOR_PALETTE`. `withAlpha(lane.color, 0.85)` is only the
  `'lane'` branch.
- **Every arc also carries `fill-opacity` — 0.88, or 0.35 when cancelled**
  (`renderer.ts:812`). Any contrast calculation that ignores it is wrong, and an earlier
  draft of this document ignored it.
- **`withAlpha` is a no-op on hex** (`utils.ts:170`): its regex matches `rgb()`/`rgba()`
  only and returns the input unchanged otherwise. The lane colour control is
  `<input type="color">` (`dialogs.ts:88`), which emits `#rrggbb`. So for any
  user-picked lane colour the 0.85 never applies and the arc is fully opaque. **This is a
  live bug on the path this design touches.**
- The label sits on a composite, not a colour: disc radial gradient, then the lane band at
  0.25 (`renderer.ts:568`), then the arc fill, then `fill-opacity`, then for cancelled
  activities a diagonal stripe pattern painted *above* the fill (`:836`).

**On numbers.** An earlier draft published a contrast table. Those figures reproduced
under no stated compositing model, because the model omitted `fill-opacity` and the lane
band. **This design deliberately publishes the method rather than the numbers**, and
requires the implementation to ship the calculation as a test. What survives independent
recomputation under every model tried:

- White labels fail WCAG AA on **8 of 8** lane colours in light mode; `#16202e` passes on
  all 8. Amber is worst, red is the best case for white.
- On the default `activity.color` path, **both** polarities fail on several palette
  entries. A two-colour picker is not sufficient.
- **In dark mode, an oracle two-colour picker still fails AA on 3 of 8 lane colours.**
  This is a defect in the mechanism, not an open question.

- `renderer.ts:846` clamps activity label size to `max(7, min(9, …))` — 7 to 9 units on
  an 800-unit viewBox, roughly 6-8 CSS pixels on a laptop.
- `renderer.ts:878` reads `if (textLen <= arcLen) { …draw… }` with **no else branch**.
  A title longer than its arc is not truncated. It is not drawn.
- Lane border labels are a **second, separate** implementation of the same idea at
  `renderer.ts:557` and `:600-626`, with its own clamp of `max(8, min(12, …))`.

**One observation, and its limit.** A first-timer did a real task unaided and nothing
surprised the author. That proves the tool is learnable. It cannot detect "I squint at
this every Monday", because a novice doing one task never reaches the daily-use
complaint. Observation and feedback are different channels, and only the feedback
channel named the disc.

## Status Quo

Users read the disc by hovering. The only fallback for an unlabelled or unreadable arc
is a native `<title>` tooltip.

That fallback does not exist in print, in the PNG export, in the SVG export, in the
animated flyover, or on a wall display with no mouse. **Four of the five surfaces
shipped in the disc-as-clock design render arcs that nobody can identify.** The author
of that design, and of three of its four export buttons, was the same advisor who spent
the first half of this session arguing the problem was the toolbar.

## Target User & Narrowest Wedge

**The user is a coworker glancing at the disc to answer "what is happening around now".**
They are not learning the tool; they learned it months ago. They want to read a label.

**The wedge** is legibility of text on the disc, and nothing else. Explicitly excluded:
toolbar progressive disclosure, `!important` removal, component abstraction, dark-mode
rework, and a full audit of the 44 colour tokens.

## Constraints

- **Colours are user data.** Lane and activity colours live in SQLite and are chosen by
  users. Contrast cannot be fixed by picking a better palette, because the palette is not
  yours to pick. The label colour must be derived from whatever colour the arc actually
  is, at render time.
- **CSS cannot reach the disc.** `cssVar()` snapshots computed styles into SVG attributes
  during render. There is no live binding. Any token the disc must obey lives in
  TypeScript and is mirrored into `:root`, never the reverse.
- **Curved text stays.** The flip-in-bottom-half behaviour is deliberate and shipped; this
  design works within it rather than replacing it.
- **No new runtime dependency.** Consistent with the rest of the project.

## Premises

All six confirmed by the user.

1. The disc is the product. Cluttered and hard-to-find are real, but a disc that cannot
   communicate has no advantage over a table.
2. "Hard to read" has a measurable physical cause: the WCAG failures above, a 7-9 unit
   clamp, and labels that are dropped rather than truncated.
3. The drop is worse than it looks, because the tooltip fallback is absent from four of
   the five export and display surfaces.
4. CSS tokens structurally cannot reach the disc.
5. **The maintainability case was overstated.** All 44 `--cp-` tokens are colour tokens —
   the part that already works. The `!important` count was also misreported twice: 36 is
   a count of *lines*, there are 51 raw occurrences, and top-level declarations number
   **6** (`:427-428` toolbar dark mode, `:584-586`, `:592` milestone sizing), not 2. The
   conclusion holds — the large majority sit inside `@media print`,
   `body.display-mode`, `prefers-reduced-motion` and width breakpoints, so "kill the
   `!important`" would have broken print and the flyover — but the precise figures in the
   earlier draft were wrong and should not be cited.
6. Because colours are user data, the fix must compute per-arc rather than choose
   per-palette.

## Cross-Model Perspective

An independent Claude subagent reviewed a structured summary with fresh context. Every
checkable claim was verified against the repo before being accepted; all held.

**Its steelman:** the disc is the product and everything else is CRUD chrome a
spreadsheet could do. Ship a legibility pass and extract only the token layer that pass
actually needs.

**The answer it called most revealing:** *"Hard to read — text on the disc."* Its
reasoning: the other two complaints are subjective and unfalsifiable, and you can spend a
month on them without knowing whether you won. This one has a physical cause in about
fifty lines.

**What it got right that this session had wrong.** It stated that the advisor "caved on
the sequencing, and his stated reason for caving is factually wrong on this repo", then
proved it: all 44 tokens are colour tokens so there is no type or spacing scale to
document; ~30 of the 36 `!important` are deliberate mode overrides rather than debt; and
none of it reaches the disc regardless. Verified: 34 of 36, and only 2 at top level.

**The finding nobody had named:** for any arc shorter than its title the label is not
drawn at all, and the only identification is a tooltip that does not exist in print, PNG,
SVG, flyover, or on a wall TV. Its conclusion — "that is not a polish issue; it's the
disc failing to communicate, which is the only reason to draw a disc instead of a table."

**Its prediction, recorded so it can be tested:** if asked *where* they meant, users will
point at the rings rather than the toolbar and the dashboard. It named this explicitly as
the evidence that would prove it wrong.

**Where this design differs.** It proposed splitting `LANE_COLORS` into a saturated base
and a derived tint. That is a palette change, and premise 6 says palette changes cannot
fix contrast when colours are user data. The halo and computed label colour subsume it,
so the split is dropped.

## Approaches Considered

### Approach A: Contrast and truncation
`readableOn()` by luminance, ellipsis instead of dropping, clamp raised to 10-13. Effort
S, risk low. **Not chosen:** leaves lane border labels on their own duplicate code path,
and offers nothing for arcs too small to hold any text.

### Approach B: Legibility as a system *(chosen)*
All of A, plus one shared label helper across both paths, a stroke halo via
`paint-order`, a hover readout for unrenderable labels, and the small type scale this
work actually requires. Effort M, risk medium.

### Approach C: Stop drawing text on the arcs
Leader lines to an outer ring, or numbered arcs with a legend. Effort M/L, risk med-high.
**Not chosen:** it removes the constraint by removing the thing the project exists to
look at, adds its own density problem across four rings, and discards shipped work.

## Recommended Approach

**Approach B**, with the scope corrected after review. The deciding argument is premise 6:
colours are user data, so someone can pick a colour tomorrow that no palette decision
anticipates.

1. **`utils.ts` — `labelStyle(fill, fillOpacity, backdrop, theme) → { color, haloColor,
   haloWidth }`.** Not `readableOn(fill: string)`: that signature cannot see the three
   things that decide the answer. It must composite the disc background, the lane band at
   0.25, the arc fill, and `fill-opacity` (0.88, or 0.35 cancelled), then pick against the
   result.

   **It must derive a colour, not choose between two constants.** In dark mode a
   two-valued picker fails AA on 3 of 8 shipped lane colours even with perfect choice, so
   the helper darkens or lightens until it clears 4.5:1. Two constants cannot satisfy the
   success criteria and shipping against them would be shipping against something
   unreachable.

2. **One shared label helper** across `renderOccurrence` (`renderer.ts:846-895`), the lane
   border labels (`:557`, `:600-633`) and the done-checkmark (`:908`, a *second*
   unconditional `'white'` the earlier draft missed). The paths differ in shape — lane
   labels are a fixed string repeated six times over a 60° span sized from `borderT`;
   activity labels are one variable-length string over a variable span sized from
   `subHeight` — so the helper takes `(text, availableLength, fontSize, style)` and the
   callers keep their own geometry.

3. **Stroke halo, in the OPPOSITE polarity to the glyph.** Dark text takes a light halo,
   light text a dark one. Not the arc's own colour: a same-colour halo separates nothing.
   Specify all four properties, because SVG defaults will not do: `paint-order="stroke"`,
   `stroke-linejoin="round"` (glyph corners spike without it), `stroke-width` ~2 units at
   the sizes in play, and the halo colour from item 1.

   **Set them as attributes, never from a stylesheet.** Tested this session:
   `paint-order` applied from a CSS rule computes correctly in the live page and is
   **silently dropped** by `serializeSVGWithStyles`, because `cloneNode(true)` does not
   carry stylesheet-derived styles and `paint-order` is not among its 11 whitelisted
   properties. As an attribute or inline style it survives, since the whitelist is
   additive rather than a filter. A stylesheet halo would look right on screen and vanish
   in print, PNG, SVG and the flyover — the same failure mode as the dead `@media print`
   palette, in a different property.

4. **Decouple the height gate from the type clamp.** `renderer.ts:847` reads
   `if (subHeight >= fontSize + 3)`, so raising the clamp floor from 7 to 10 also raises
   that gate from `>= 10` to `>= 13`, and labels at subHeight 10-12 that render today
   would stop rendering. Real geometry lands there: 5 lanes × 4 sub-rows gives ~10.6.
   Keep the gate at its current effective threshold and let font size float, or make the
   clamp radius-aware — inner rings at r≈100 and outer arcs at r≈350 have very different
   character budgets. **An earlier draft raised the clamp without noticing this, which
   would have caused label loss in exactly the case item 5 exists to prevent.**

5. **Truncate, never drop.** Replace the bare `if (textLen <= arcLen)` at `:878` with
   truncation to an ellipsis. Measure the full string once, estimate the cut index from
   near-linear advance width, then verify with **one** more measurement — two measurements,
   not a six-iteration binary search. Each measurement appends a hidden `<text>`, forces
   synchronous layout via `getComputedTextLength()`, and removes it; that cost runs per
   *occurrence*, not per activity, and a Year-zoom view with recurrence expansion can carry
   several hundred. `renderer.ts:1048` already has an iterative-shrink precedent to reuse.

6. **A mouseless fallback for arcs that hold no text.** The earlier draft proposed a hover
   readout, which buys nothing on the five surfaces this design names as the problem —
   print, PNG, SVG, flyover and wall display are all mouseless. Either the arc gets a
   drawn identifier that survives export (a numbered badge with a legend), or the design
   states plainly that sub-three-character arcs are unlabelled in export and accepts it.
   **This is the one open design decision left in the approach.**

**Cut after review, as out-of-wedge:** the TYPE scale (this work needs two numbers, both
already TS constants at `:557` and `:846`; mirroring 11 CSS sizes touches auth, dashboard
and dialogs, none of which is the disc), and `DESIGN.md` (one true sentence belongs in
`CLAUDE.md` under existing patterns, not a new file).

## Open Questions

1. ~~Does the halo survive export?~~ **Resolved by test.** Attribute and inline-style
   halos survive; a stylesheet halo is silently dropped. Now a hard rule in item 3.
2. **What identifies an arc too small for any text, on a mouseless surface?** Numbered
   badge with a legend, or accept the loss and say so. This is the one real design
   decision still open, and it is the last thing standing between this design and success
   criterion 3.
3. **What is the readable floor on a wall display?** The clamp is being reasoned about,
   not measured. Nobody has looked at the disc from across a room, and that is the surface
   the disc-as-clock design added.
4. **`withAlpha`'s hex no-op** (`utils.ts:170`) is a live bug on this path: user-picked
   lane colours are fully opaque rather than 0.85. Fixing it changes every arc's
   appearance for existing planners, so it is a deliberate call, not a tidy-up. Flagged,
   not scoped.
5. **Cancelled activities are a genuinely unsolved case.** `fill-opacity: 0.35` plus a
   diagonal stripe pattern painted above the fill (`:836`) means the glyph run crosses two
   backgrounds. A single label colour is provably wrong for part of it; the halo mitigates
   but does not resolve this.
6. **Cluttered and hard-to-find remain untouched**, deliberately. The assignment below is
   what decides whether they are the next project.

## Success Criteria

- No activity or lane label falls below 4.5:1 against **the composite it is actually drawn
  on** — disc background, lane band, arc fill and `fill-opacity` — for every colour in
  `COLOR_PALETTE`, `STATUS_COLORS` and `LANE_COLORS`, **in both themes**. Verified by a
  test that computes the ratio and ships the compositing model, not by eye.
- The four palette colours where neither white nor dark clears 4.5:1, and the three lane
  colours that fail in dark mode, are the acceptance cases. If the helper cannot pass
  those, it is not done.
- No arc whose geometry admits three characters renders without a label, and raising type
  size does not reduce the number of labels drawn — measured before and after against the
  same planner.
- Every arc is identifiable in print, PNG, SVG, the flyover and on a wall display, or the
  design states explicitly which arcs are not and why.
- Activity labels, lane labels and the done-checkmark all obtain their colour from one
  helper.

## Distribution Plan

Existing pipeline. Client-side only, `npm run build:client` into the embedded `public/`,
no new dependency, no packaging change, no migration. It reaches the air-gapped box
through the same tarball as everything else.

## Dependencies

- None external. But `labelStyle` is **not** "arithmetic": it is a small compositing
  model over gradient, lane band, fill and `fill-opacity`, in two themes. It is the piece
  most likely to be wrong, and it needs the test before it needs the renderer wiring.
- Item 4 is unblocked: the halo must be an SVG attribute, settled by test.
- Item 3 (shared helper) should land before items 4-6, so each fix is written once.

## The Assignment

**Ask the coworkers who said "cluttered" and "hard to find" where they meant — the rings,
or the chrome.** One question, one day.

The cold read staked its position on this: it predicts they point at the rings, which
would mean all three complaints are the same complaint and this design covers them. If
instead they point at the toolbar and the dashboard, then two of three are chrome
problems and the toolbar work I argued for at the start of this session gets its
justification back — from users this time, rather than from me counting buttons.

Either way it decides what happens after this, and it costs a conversation.
