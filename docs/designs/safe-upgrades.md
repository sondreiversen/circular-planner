## Problem Statement

Upgrading the air-gapped production instance is a held-breath operation. A tarball is
built on an internet-connected machine, physically carried to the production box, and
applied by `install-airgap.sh`. That machine holds a production database whose data has
to survive. Nothing in the current upgrade path guarantees that it will.

The session opened as "a backend overhaul." It is not one, and saying so early is the
most useful thing this document does. The cost named was upgrades, not architecture.

## Demand Evidence

Not a market question — this is internal infrastructure — so the equivalent evidence is
what the deployment actually does today, all verified by reading the repo:

- `main.go:154` calls `db.Migrate()` unconditionally at startup. There is no opt-out.
- `install-airgap.sh:194` copies the new binary over the running one. **The previous
  binary is not kept.** On an air-gapped box with no registry and no network, recovering
  from a bad build means physically carrying the old tarball back.
- `scripts/backup.sh` is well written, handles SQLite and Postgres, and is **never
  invoked by anything**. `install-airgap.sh:215` prints its name in an info message.
- `backup.sh`'s safe path shells out to the `sqlite3` CLI. Neither `install-airgap.sh`
  nor `package-airgap.sh` installs or packages it, and the app does not need it — it
  embeds `modernc.org/sqlite`. So the *likely* path on a minimal box is the fallback: a
  raw `cp` of a live WAL database, which warns and proceeds.
- `doctor.sh:118` skips its backup-disk check whenever `BACKUP_DIR` is unset (the
  variable defaults to empty at `:116`), and the
  installer never sets it. The one check that could have surfaced "you have no backups"
  is a no-op in every real install.
- `install-airgap.sh:258` runs `doctor.sh` as `|| true`, with a comment stating the
  preflight is deliberately non-fatal.

## Status Quo

An operator carries a tarball to the box and runs `install-airgap.sh u`. The script
copies a new binary over the old one, prints a preflight it cannot act on, and tells the
operator to restart. The restart applies every pending migration silently. If anything is
wrong afterwards, there is no previous binary, no enforced backup, and no verified one.

Recovery today depends entirely on the operator having remembered, unprompted, to run a
script the installer only mentions by name.

## Target User & Narrowest Wedge

**The user is the operator standing at the air-gapped machine**, possibly the author,
possibly not, holding a USB stick and a maintenance window. What they need is not a
better architecture. It is the ability to undo what they just did without leaving the
room.

**The wedge** is the complete safe-upgrade path and nothing else: a backup that does not
depend on absent tools, a gate that refuses rather than warns, an end to silent
migration, a kept previous binary, and a restore proven by test rather than by hope.
Explicitly excluded, and confirmed excluded by the user during the session: the
1468-line planners handler, and the last-write-wins sync model.

## Constraints

- **Air-gapped production.** No network, no registry, no package manager, no ability to
  install a missing tool. Anything the design needs must arrive in the tarball.
- **Physical transfer.** Fix-forward costs a trip, so it cannot be the primary recovery
  strategy.
- **Bare metal, `MODE=2`** (confirmed during the session). The scripts are present and
  `doctor.sh` does run on upgrade. The Docker path is a separate, currently-unused risk.
- **Production data must survive** any update or schema change.
- **Installs and updates stay a single easy-to-run script.** Whatever this adds must not
  turn the upgrade into a runbook.

## Premises

All six were confirmed by the user.

1. "Upgrades are dangerous" means the whole delivery chain, not just schema. The
   migration runner is the **best**-defended link: 18 migrations, zero destructive DDL
   (no `DROP`, no `RENAME`, no `TRUNCATE`), each wrapped in a transaction whose
   `schema_migrations` row is written atomically alongside it (`migrate.go:186-212`).
   Precisely: not all are *purely* additive — `005-admin-role.sql:2` mutates rows with
   `UPDATE users SET is_admin = 1 WHERE id = (SELECT MIN(id) FROM users)`. Mutating, not
   destructive. **The failure mode this design guards is a migration that SUCCEEDS and is
   wrong, never one that fails** — failures already roll back cleanly.
2. The undefended links are the binary overwrite and the absence of any enforced backup.
   Neither is about migrations.
3. `backup.sh`'s safe path needs a CLI the deployment never installs, so the fallback is
   the likely path.
4. `VACUUM INTO` in the already-embedded pure-Go driver is a verified replacement.
   **Tested twice during this session** against `modernc.org/sqlite v1.35.0`: once with an
   uncommitted transaction open, and once under a goroutine committing continuously. The
   second is the real upgrade scenario — it completed in 4 ms, produced `integrity_check
   ok`, and captured 33,479 rows against 33,790 live, exactly the point-in-time behaviour
   a snapshot should have.

   It is **not atomic** and the doc should not say so. It is a *transactionally consistent
   point-in-time snapshot as of read-transaction start*; writes committed while it runs
   are absent. Its non-blocking property depends entirely on `db.go:75` opening SQLite in
   `journal_mode(WAL)` — under a rollback journal the same read transaction would block
   every writer for its full duration. **WAL is a load-bearing precondition, not an
   implementation detail.**
5. The single highest-value change is keeping the previous binary. It is about five lines
   and needs no design doc.
6. This is deployment safety, not architecture.

## Approaches Considered

### Approach A: Reversibility first, minimum edits
Keep the previous binary, call `backup.sh` from the upgrade path, set `BACKUP_DIR`, let a
doctor FAIL abort. Effort S, risk low. Ships in an afternoon. **Rejected as the whole
answer** because it leaves the backup depending on a CLI that is not installed, so the
artifact you would restore from may be a torn copy of a live WAL database. Its
reversibility half is retained inside B.

### Approach B: Backup moves into the binary *(chosen)*
`planner backup [--verify]` via `VACUUM INTO`, a manifest, a `MIGRATE_ON_STARTUP` switch,
`migrate apply` gated on a fresh verified backup, previous binary kept, CI restore
round-trip. Effort M, risk medium.

### Approach C: Versioned releases with a symlink flip
`releases/<version>/`, `current ->` symlink, `shared/data/` outside every release.
Rollback becomes a symlink flip and you keep N versions. Effort M/L, risk medium.
**Not chosen now:** it restructures the on-disk layout of a live install on a machine
reachable only by physical trip, which is a larger one-way door than the problem
currently warrants. Recorded in Open Questions as the intended end state.

## Recommended Approach

**Approach B.** It removes the missing-tool dependency rather than routing around it,
using a mechanism verified against the exact embedded driver during this session. Because
the safety lives in the binary — the one artifact guaranteed to be present — it also
covers the Docker path without being aimed at it.

Build order matters more than usual here, because the cheapest item is also the most
valuable.

**0. Prerequisite: an idempotent `.env` writer.** The upgrade branch of
`install-airgap.sh` (lines 192-204) copies the binary and scripts and touches nothing
else; `.env` is written only in the fresh-install branch, at line 218. So any design that
"sets a variable in `.env`" never reaches the one machine this document exists for. Add
`ensure_env_var KEY VALUE` — grep for the key, append if absent, leave existing values
alone — and call it from **both** branches. Items 4 and 6 are dead without this.

1. **Keep the previous binary.** `mv planner planner.prev` before the copy at
   `install-airgap.sh:194`, and print the rollback command in the summary. Five lines.
   Do this first, on its own, before anything else here.

2. **`internal/db/backup.go` + a `backup` subcommand**, mirroring the existing `migrate`
   block at `main.go:63`. SQLite uses `VACUUM INTO`. Postgres keeps `pg_dump` but
   **hard-fails** when absent rather than warning. Required behaviours:
   - **Refuse if the resolved database file does not already exist.** `loadDotEnv()`
     (`main.go:489`) reads `.env` from the *current working directory* and the DSN is
     relative (`sqlite:./data/planner.db`), so running `planner backup` from the wrong
     directory would otherwise create an empty database, snapshot it, pass
     `integrity_check`, and satisfy the gate. A backup of the wrong file is worse than no
     backup, because it looks like success.
   - **Write to `<name>.partial`, verify, then `rename()`.** A killed vacuum must not
     leave a file that a later check mistakes for a backup.
   - **Open its own connection with its own DSN**, not `db.Open`. The app pins
     `SetMaxOpenConns(1)` (`db.go:86`) and `temp_store(MEMORY)` (`db.go:81`); the backup
     should inherit neither. `temp_store(MEMORY)` in particular means a vacuum's index
     rebuild sorts in RAM, which is a poor trade on a small box.
   - **Concurrency rule, stated once so items 2 and 5 cannot drift apart:** the backup may
     run inside the `migrate apply` process, but only on its own dedicated connection and
     only before any migration transaction is open. What is forbidden is invoking it from
     a request handler or anywhere a `Tx` may already be live — with `SetMaxOpenConns(1)`
     that deadlocks on the single connection rather than failing cleanly. Verified: SQLite
     refuses `VACUUM INTO` from inside a transaction outright (`cannot VACUUM from within
     a transaction`), so the misuse errors rather than corrupting, but the deadlock risk
     against the shared pool is real and is why the backup gets its own connection.
   - **Clear any stale `.partial` before starting.** Verified this session: `VACUUM INTO`
     refuses a destination that already exists (`output file already exists`). A killed
     backup therefore poisons its own retry unless the leftover is unlinked first.

3. **`planner backup --verify`**: reopen the dump, `PRAGMA integrity_check`, count rows in
   `users`, `planners`, `activities`, compare against source. Write a manifest **last**,
   as the commit record: absolute resolved source path, bytes, row counts, and schema
   state expressed as *count and highest filename from `schema_migrations`* (there is no
   version integer — `migrate.go:205` stores filenames).

4. **`MIGRATE_ON_STARTUP`** in `internal/config`, matching the existing
   `os.Getenv("X") != "false"` house style at `config.go:54`. Default `true`. The
   installer writes `false` via item 0, on both fresh installs and upgrades. Note plainly:
   **this does change behaviour for the existing box** — that is the point, and it is the
   one intentional behaviour change in this design. When false with migrations pending,
   the server logs the pending list and exits non-zero naming the exact command.

5. **`migrate apply` takes its own backup** immediately before migrating, on its own
   connection per item 2, and aborts if the backup or the verify fails. `--no-backup` is
   the escape hatch; it logs loudly and records its use in the manifest directory so
   `doctor.sh` can report it.

   **Short-circuit when nothing is pending.** `main.go:132` currently calls `db.Migrate()`
   unconditionally, so `migrate apply` with an empty queue would take a full backup for no
   reason. Check `ListPending()` first and skip both the backup and the migration.

   **The honest weakness, named rather than buried:** aborting on backup failure can
   reproduce the very objection used to kill the mtime gate. Disk full at 2 a.m., migrate
   refuses, operator reaches for `--no-backup`, and by the third upgrade it is in the
   runbook. This design mitigates rather than eliminates that: check free space *before*
   starting the dump and fail with the specific remedy and the exact override command, so
   the failure is diagnosable in ten seconds instead of being a wall. But a gate that can
   refuse can always be bypassed, and the mitigation is that `doctor.sh` reports every use
   of the bypass, making the ritual visible instead of invisible.

   **This replaces an earlier design that gated on "a verified backup newer than the
   database's mtime". That check was unsound and testing killed it.** In WAL mode commits
   land in `planner.db-wal`; the main file's mtime only advances on checkpoint. Measured
   this session: 200 committed rows left `planner.db`'s mtime completely unchanged, so a
   backup taken *before* those writes still tested "newer than mtime" and passed. It also
   fails the other way — stopping the service checkpoints and deletes the WAL, bumping
   mtime to *after* a backup taken sixty seconds earlier, so the gate would refuse a
   perfectly good backup and train the operator to reach for `--no-backup` on day one. And
   air-gapped boxes have no NTP. Taking the backup makes freshness structural instead of
   inferred, and deletes the whole question.

6. **Set `BACKUP_DIR`** via item 0 so `doctor.sh:118` stops skipping, and add a doctor
   check for the age of the newest verified backup and whether `--no-backup` was used.

7. **Replace `restore.sh`'s unsafe paths too.** It is half the recovery story and the
   design cannot condemn `sqlite3`-or-`cp` everywhere else while leaving it at
   `restore.sh:62-68`. It must also **verify the dump before overwriting** the live
   database, which it currently does not.

8. **CI round-trip test**: seed a database, back up, apply a migration, restore, assert
   row counts match. `internal/db/` holds only `rebind_test.go` today, so this is new test
   infrastructure rather than an addition — small, but not free. An untested restore is
   not a restore.

**Relationship to Approach A:** A is not really rejected, it is *first*. Items 0 and 1
are Approach A and they ship today. Items 2-8 are the follow-on that makes the backup
trustworthy. The document earlier called A "rejected as the whole answer" — as the whole
answer, yes; as the opening move, it is the highest value-per-line work here.

## Open Questions

1. **Where does the backup physically live?** It would land in `./data/backups` — the
   same disk it protects. (Earlier wording said "inside the directory `restore.sh`
   overwrites"; that was wrong. `restore.sh:90` overwrites `$SQLITE_PATH`, the live
   database, and only *writes into* `backups/`.) The same-disk risk is real regardless:
   one failed disk takes the original and every copy. Air-gapped arguably means the copy
   should leave on the same removable media the tarball arrived on. Nothing here does
   that yet, and it may be the most important unanswered question in this document.

2. **Free space — a smaller worry than an earlier draft claimed.** That draft said a long
   read transaction blocks WAL checkpointing so `planner.db-wal` grows *unbounded* during
   the backup. Two corrections. First, the mechanism is milder: a passive checkpoint still
   copies pages up to the oldest reader's mark; what it cannot do is reset and truncate the
   WAL, so the file grows by append rather than being pinned. Second, and more to the
   point, **item 4 removes the concurrent writer entirely** — with
   `MIGRATE_ON_STARTUP=false` the server has exited before `migrate apply` runs, so there
   is nothing committing during the vacuum and the WAL tail is roughly zero. The measured
   4 ms on 33k rows refutes "unbounded" as well.

   What remains is ordinary and worth a precheck: the dump is roughly the size of the
   database, and it lands on the same disk. Check free space before starting. The residual
   risk is a *live* backup taken outside the upgrade flow, where a writer is active — that
   one does need the larger budget.

3. **Approach C, versioned releases**, as the eventual end state.

4. **The Docker path** remains unguarded for anyone installing with defaults —
   `install-airgap.sh:52` defaults to `MODE=1`, the runtime image carries only the binary,
   and `package-airgap.sh:184` ships `scripts/` under `bare-metal/` alone. Not today's
   production risk, since production is bare metal. Still a loaded gun. Moving backup into
   the binary happens to disarm most of it.

5. **The window this design does not close:** a migration that succeeds and is wrong. The
   backup predates it, so restoring loses every edit made between the upgrade and someone
   noticing. On a planner people edit continuously that window is the real cost, and only
   the binary rollback shortens it.

6. **Postgres is under-specified.** Item 2 keeps `pg_dump`; everything about snapshot
   semantics and WAL here is SQLite-specific. Either state that the safety story covers
   SQLite only and Postgres gates on manifest age, or scope the work to SQLite and say so.

## Success Criteria

- `planner backup --verify` produces a dump that passes `integrity_check` and matches
  source row counts, **on a box with no `sqlite3` CLI installed** — which is every box,
  since neither installer ships one.
- `planner backup` **refuses** when pointed at a path where no database already exists,
  rather than snapshotting an empty file it just created.
- An upgrade that goes wrong is undone **without leaving the room**: previous binary
  restored, or database restored from a backup `migrate apply` took moments earlier.
- `migrate apply` aborts if its own backup or verify fails, and says exactly what to do.
- A restart with `MIGRATE_ON_STARTUP=false` and pending migrations exits non-zero with the
  pending list, rather than migrating.
- Running the upgrade twice in a row leaves one copy of each `.env` key, not two.
- CI proves the **restore** path on every push, not just the backup path.
- The upgrade is still one script an operator runs without a runbook.

A note on what "restored from a backup taken moments earlier" means, since the doc
previously overstated it: the dump is consistent as of the *start* of its read
transaction, not the instant the command returned. Edits committed during the vacuum are
not in it. That is correct snapshot behaviour, not a defect, but the operator should not
be told the backup captures the moment they pressed enter.

Existing pipeline covers it. Everything ships inside the same air-gap tarball:
`package-airgap.sh` already packages the binary and `bare-metal/scripts/`, and the new

One packaging change worth making regardless: `package-airgap.sh:184` copies `scripts/`

## Dependencies

- No new Go modules. `VACUUM INTO` works in the already-embedded `modernc.org/sqlite`
  v1.35.0 — verified this session.
- No new npm packages, and no change to the air-gap tarball's shape.
- Item 1 (keep previous binary) depends on nothing and should land first.
- **Items 4 and 6 depend on item 0.** Without an idempotent `.env` writer they never
  reach an existing install, because the upgrade branch does not write `.env` at all.
- Items 4 and 5 are coupled: having `migrate apply` own the backup only matters once
  startup migration can be turned off, or the operator never reaches `migrate apply`.
- Item 2's safety depends on `db.go:75` keeping `journal_mode(WAL)`. A future DSN change
  would silently convert the backup into a global write lock.

## Implemented (2026-08-28)

All eight items are built and verified against a running install. Two bugs
surfaced only when the whole path was exercised end to end, and both would have
shipped.

**Item 1 — previous binary kept.** `mv planner planner.prev` before the copy,
with the rollback command printed. Verified with two distinguishable binaries
and a live process: the running service survives its own binary being renamed,
and the printed command restores the old build.

**Items 2 and 3 — backup in the binary.** `planner backup [--no-verify]
[--no-prune]` via `VACUUM INTO`. Proven with `PATH=/nonexistent`: the backup
completes with no external tool reachable, which is the whole argument for
moving it out of a shell script. Refuses a source that does not exist, clears a
stale `.partial` first, writes `.partial` then renames, and writes the manifest
last as the commit record. Verification compares row counts against source, not
just `integrity_check` — a structurally perfect backup of the wrong database
passes `integrity_check` every time. Retention gained a keep-last-N cap; a test
caught the first implementation pruning a long-idle instance to nothing, since
with age-only rules every dump is old when nobody has upgraded in months.

**Items 4 and 5 — the silent path is closed.** `MIGRATE_ON_STARTUP` defaults
true so upgrading changes nothing by itself; the installer sets it false. With
migrations pending the server lists them and exits non-zero naming the exact
command, because under systemd a silent start against a half-expected schema is
worse than a failed one. `migrate apply` now takes its own verified backup,
short-circuits when nothing is pending, checks free space first, and records
every `--no-backup` use.

**Items 0, 6, 7, 8 — the installer and recovery side.** `ensure_env_var` reaches
existing installs, which nothing previously did. `doctor.sh` gained checks for
backup freshness, unverified backups, and bypass usage. `restore.sh` no longer
depends on the `sqlite3` CLI and verifies a dump before overwriting anything. A
round-trip test proves the restore actually restores.

### The two bugs that only appeared under test

**`migrate status` is not a validity check.** restore.sh first used it to verify
a dump. It reports "0 applied, N pending" for a file that is not a database at
all and exits zero, because an un-migrated database and an unreadable one look
identical to it. Restoring on that basis overwrote a healthy database with a
text file — observed live, going from `Applied: 18` to `Applied: 0`. Replaced
with `planner verify`, which runs `integrity_check` and requires a non-empty
`schema_migrations`, so an empty file SQLite happily opens is rejected too.

**Second-granularity backup names collide.** restore.sh takes a safety dump
moments before restoring, so the safety dump silently overwrote the dump being
restored via `os.Rename`, and the restore became a no-op that reported success.
Filenames now take a `-2`/`-3` suffix on collision. Proven fixed: a restore that
previously changed nothing now rolls `users` from 2 back to 1.

Neither was findable by reading. Both needed the thing to actually run.
